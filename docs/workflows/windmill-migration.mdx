# Windmill migration

Six generation workflows are represented as Windmill flows under
`f/lumenclip`. Their display names follow `APP_NAME - WORKFLOW_NAME` with
`APP_NAME` fixed to `lumenclip`.

| Workflow ID                   | Windmill display name                     | Windmill path                             |
| ----------------------------- | ----------------------------------------- | ----------------------------------------- |
| `slideshow-generation`        | `lumenclip - slideshow generation`        | `f/lumenclip/slideshow_generation`        |
| `ugc-video-generation`        | `lumenclip - UGC video generation`        | `f/lumenclip/ugc_video_generation`        |
| `react-reveal-generation`     | `lumenclip - React & Reveal generation`   | `f/lumenclip/react_reveal_generation`     |
| `greenscreen-meme-generation` | `lumenclip - Greenscreen Meme generation` | `f/lumenclip/greenscreen_meme_generation` |
| `linkedin-generation`         | `lumenclip - LinkedIn generation`         | `f/lumenclip/linkedin_generation`         |
| `x-threads-generation`        | `lumenclip - X and Threads generation`    | `f/lumenclip/x_threads_generation`        |

Each workflow has an explicit DAG. Logical input groups resolve in named
branches, independent work runs in parallel, and downstream modules receive
only named dependency artifacts. No generated flow uses a cumulative
`results.a ?? results.b` fallback chain.

Named workflow runs accept the same top-level fields as the Windmill form.
Linear `startAt`/`stopAfter` windows are rejected because they cannot preserve
branch dependencies. For isolated testing, Windmill MCP runs
`f/lumenclip/workflow_stage_runtime` directly with `runScriptByPath`.

Slideshow validation joins only template/schema, collections/assets, and word
variables. Model settings are loaded inside the text path, while static image
candidates are prepared independently. Generated text and candidate pools
first meet at caption-based shortlisting. Usage history, prior runs, web
research, similarity repair, translation, and slideshow MP4 post-processing
are absent from the generation workflow.

UGC loads template defaults once. Product and script component resolvers do
real merge/validation work before script generation; actor/motion and voice
join at lip-sync; the resulting performance joins B-roll and render settings at
composition. Each parallel checkpoint job uses an isolated component run.
React & Reveal and Greenscreen Meme similarly use real role resolvers and media
staging, while draft metadata first joins after rendering. LinkedIn branches
run actual group normalizers. X/Threads loads and validates the template while
normalizing topic/source input, then prepares text persistence and the optional
image task independently before image attachment.

The source-level dependency audit lives in
`windmill/workflow-dependencies.ts`. Generated-flow tests reject the generic
identity artifact source and assert the recorded producer-to-consumer order.

## App boundary

`lumenclip_pipeline_run` queues a Windmill flow. It never executes a named
stage loop inside the Next.js process. Individual stages remain callable
through Windmill MCP's native `runScriptByPath` tool, without a LumenClip
callback route or wrapper flow.

## Required configuration

The Lumenclip web service requires `WINDMILL_BASE_URL`,
`WINDMILL_WORKSPACE_ID`, and `WINDMILL_TOKEN`.
The Windmill workspace requires `f/lumenclip/internal_base_url` and the secret
variable `f/lumenclip/shared_secret`.

## Deployment state

The six flows embed the private stage boundary directly; there is no shared
`f/lumenclip/run_pipeline_stage` script to deploy or keep synchronized.

The first migration slice moves orchestration out of the app. Stage handlers
remain behind the private Lumenclip boundary while they are moved into
Windmill-native scripts. Composite stages can therefore still contain nested
provider calls during this transition.
