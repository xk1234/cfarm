# Slideshow generation pipeline

Templates define text rules and a catalog of independently styled slide designs.
They do not define a recurring schedule or social destination. Every run is an
explicit request that produces an unpublished draft; publishing or scheduling
that completed output happens later in the output viewer or publishing API.

## Run this

<Tabs items={['MCP', 'HTTP', 'App']}>

<Tab value="MCP">

```json
{
  "tool": "lumenclip_slideshow_generate",
  "arguments": {
    "templateId": "template_123",
    "requestId": "draft-2026-08-07-001",
    "hook": "optional exact topic seed"
  }
}
```

`templateId` is required. `requestId` and `hook` are optional. Omitting `hook`
allows the runner to select an enabled saved hook; if the pool is empty, the text
agent creates an original topic from the template instructions.

</Tab>

<Tab value="HTTP">

```bash
curl -X POST https://<your-host>/api/templates/run \
  -H 'Content-Type: application/json' \
  -d '{
    "templateId": "template_123",
    "force": true,
    "requestId": "draft-2026-08-07-001"
  }'
```

`force: true` means “run this saved template now”; it does not bypass QA and it
does not opt into automatic publishing.

</Tab>

## Stage map

| #   | Stage                        | Output                                                                    |
| --- | ---------------------------- | ------------------------------------------------------------------------- |
| 1   | Validate input               | Normalized template, media collections, variables, model settings         |
| 2   | Select topic                 | Exact hook, an expanded saved hook, or an agent-created topic brief       |
| 3   | Plan sequence                | Fixed slide count with agent-ordered design IDs and one purpose per slide |
| 4   | Build text schema            | One structured placeholder set for the planned designs                    |
| 5   | Generate text                | Title, caption, hashtags, and every visible text item                     |
| 6   | Similarity and word-range QA | Accepted draft or repaired/retried copy                                   |
| 7   | Select images                | One pinned, deterministic, or AI-matched image per planned slide          |
| 8   | Assemble and translate       | Styled slide objects, with optional DeepL translation                     |
| 9   | Render and store             | PNG slides, thumbnail, preview URL, and downloadable ZIP                  |
| 10  | Finalize                     | Unpublished result, run record, QA findings, and reuse-memory entries     |

## Sequence contract

The schema stores `slide_designs[]`. Each design has a stable `id`, display
`name`, agent-facing `instructions`, `collectionId`, text items, aspect ratio,
image grid, overlay, AI image-matching flag, and optional visual preset. It has
no Hook/Content/CTA role; designs can repeat within the fixed sequence.

Text settings store the fixed `num_of_slides` and `slide_planning_prompt`. The
planner must return exactly that many entries and may only choose IDs present
in `slide_designs`. Invalid IDs or a mismatched count fail before copy
generation. The text model never decides the count.

Legacy `formatting` blocks remain readable only as a migration source. When a
record has no `slide_designs`, normalization deterministically expands its old
hook/body/CTA blocks into numbered slide designs. New saves and runs use the
sequence model.

## Publication boundary

The run stores `publishMode: manual` and no template destinations. It does not
upload media to a social provider, create a scheduled publication, or enqueue a
future template run. A user or agent can later publish the completed output with
the output publication flow, including an immediate or future provider time.
