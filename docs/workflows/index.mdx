Each page covers one step of the journey twice: what an agent calls over MCP, and what a person
clicks in the app. Both surfaces hit the same domain services, so they diverge in places — where
they do, the page says so rather than describing an average.

Every page follows the same shape: the tool call with its real input and output, the UI
equivalent as a numbered table, then the failures worth checking. Tool schemas, labels, and
error strings are quoted from the code, not paraphrased.

## Before you start

**The agent surface has no per-caller identity.** `/mcp` resolves a single owner from
`LUMENCLIP_MCP_OWNER_ID` or `LUMENCLIP_SYSTEM_OWNER_ID` and runs every tool as that owner.
There is no token or scope check on the transport. The `lumenclip:read` / `lumenclip:write`
scopes described elsewhere under `mcp/` are not implemented. Read
[Signing in](/docs/workflows/signing-in) before exposing that endpoint.

**Mutating tools take a `requestId`, not an `idempotency_key`.** How strong that guarantee is
varies by tool, and each page says which kind it is.

**Two tools reach outside the app**: `lumenclip_output_publish` publishes, and
`lumenclip_ugc_generate` spends money at four providers. Both are called out where they appear.
